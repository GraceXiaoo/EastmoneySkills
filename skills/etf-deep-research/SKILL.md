# ETF一页纸2.0

## 目标与硬约束

为单只目标ETF生成中文研究报告。必须先取条件接口、再判定ETF分类、再按分类选择章节和接口。结构化数据优先使用 MQL；资讯材料优先使用 `mx-ds-mcp` 的 `mx_finance_search_news`。不得编造数据，不得把本 Skill、提示词、接口调用过程或工具来源描述写进报告。

将“逐接口执行”定义为可审计的交付条件，并将“公开溯源”定义为交付条件。凡元数据已发现、入参齐备且前置条件成立的接口，必须至少实际执行一次；其他接口已经返回相同数据、多 Block 已覆盖正文需要、报告篇幅有限或已有数据足够，均不构成免执行理由。

报告正文只呈现研究事实、分析和公开业务数据。禁止出现“通过MQL取数得到”“通过资讯搜索得到”“根据提示词”“接口返回”“取数失败”“元数据未发现”“因接口异常”等过程、来源或失败解释。不得在正文、图表、脚注、页眉页脚中写入机构代码、基金经理代码、证券内码、执行ID或其他内部编码。数据缺失时省略对应内容，不在正文解释缺失原因。

## 执行前必须读取的参考资料

每次开始 MQL 元数据检索或生成 MQL 前，必须完整读取以下文件；不得只凭记忆或接口英文名拼接脚本：

1. `references/interface_catalog.json`：接口中文名、路径提示、入参来源与预期返回字段。
2. `references/MQL取数参考文档.txt`：用户提供的 MQL 语法、`ReportBlock`、`SetCodes`、`SetReportFilter`、`REPORT_FIELD` 与 `OutputBlock` 写法参考。
3. `references/execution_audit_schema.md`：逐接口审计状态与覆盖率验收。
4. `references/provenance_schema.md`：公开溯源数据模型、脱敏与交互规范。

`MQL取数参考文档.txt` 是参考资料，不是报告正文，也不是需要逐条执行的任务清单。文档中的示例代码、示例证券、示例日期和自然语言任务不得原样继承；实际脚本仍须以本次 `Search_Context` 返回的完整元数据和本次目标参数为准。

## 三层数据隔离与公开溯源

全流程必须把信息分成三个互不混写的层：

- `report_content`：报告正文，只含中文研究内容和公开业务数据。
- `public_provenance`：仅供 HTML 用户主动点击查看的脱敏原始数据表，只含中文表名、数据日期、中文列名、原始返回值及正文引用位置；默认隐藏，不属于报告正文。
- `internal_audit`：接口名、报表路径、MQL脚本、过滤条件、执行ID、错误码、失败原因和内部字段，必须只留在 `work/`，禁止进入任何交付文件。

每个正文关键数字、数据表和图表必须绑定至少一个 `source_id`。同一原始数据表可被多个正文位置复用；不得为了制造溯源而改写原始值。公开溯源必须先执行：

```text
python scripts/etf_one_page.py provenance-validate <公开溯源.json>
```

生成三种格式后还必须执行：

```text
python scripts/etf_one_page.py report-scan <HTML文件> <Word文件> <PDF文件>
```

任一检查非0时禁止交付。公开溯源字段和交互细节见 `references/provenance_schema.md`。

### HTML 溯源交互

- 在关键数字、表格标题或图表标题旁加入统一的“查看原始数据”触发器，并通过 `data-source-id` 绑定公开溯源表。
- hover 时显示轻量提示：数据表中文标题、数据日期、行数和列数；不得显示接口、路径、脚本或错误信息。
- click 时打开可关闭、可键盘操作的对话框，展示源头请求返回的脱敏数据表；表头必须为中文，宽表允许横向滚动。
- CSS、JavaScript 和溯源 JSON 必须内联或本地随文嵌入，核心功能不得依赖网络。
- 原始数据表只能存在于默认关闭的 `<dialog>` 或等价模态层中，未点击时不得占据页面空间。禁止在正文末尾、页脚之前或任何常规内容流中集中输出原始数据表。
- 禁止生成“附录：原始数据表”“原始数据表附录”“数据溯源附录”等正文章节。打印样式必须同时隐藏溯源触发器和原始数据对话框，打印或转换 PDF 时不得带出原始数据表。

### Word 与 PDF 不展示原始数据表

Word 和 PDF 只交付研究正文、业务图表、必要数据表及风险提示，不生成原始数据表附录，不展示“数据表-001”等溯源编号，也不得把 HTML 隐藏对话框中的内容复制到文末。HTML 的 hover 与 click 是唯一面向读者的原始数据查看方式；内部审计仍保留在 `work/`，用于过程验收但不进入任何交付物。

## 必须交付的文件

除非用户明确指定只要某一种格式，每次成功生成报告必须同时交付以下三个文件，文件名使用相同主体：

- `<基金代码>-ETF一页纸.html`：适合屏幕浏览的响应式版本。
- `<基金代码>-ETF一页纸.docx`：可编辑的 Word 版本。
- `<基金代码>-ETF一页纸.pdf`：适合分发和打印的定稿版本。

三种格式必须来自同一份已核验的数据模型和报告正文，章节、数字、日期、单位、表格与图表口径必须一致。禁止分别生成三套内容。若某格式生成或校验失败，不得把其余格式描述为完整交付；应说明具体失败格式，保留已成功文件，并停止该格式的重复转换。

### 生成顺序

1. 完成结构化数据、资讯、计算结果和章节正文，形成唯一内容模型。
2. 先生成 DOCX，再生成 HTML；PDF优先由最终 DOCX 的同一次渲染流程导出，以减少分页和字体差异。只有 DOCX 转 PDF 不可用时，才使用 PDF 专用生成路径，并保持内容完全一致。
3. 创建 DOCX 或 PDF 前，先加载工作区依赖。分别遵守 `documents` 与 `pdf` 能力的创建、渲染和验证要求；开始相应格式的首次创作前，执行其规定的 artifact operation 标记命令。
4. 所有最终文件写入当前任务的 `outputs/` 目录。渲染图片、临时图表和中间文件放入 `work/` 或专用临时目录，不得混入交付目录。

### Word规范

- 使用 `python-docx` 或文档能力提供的确定性工具生成，不依赖用户本机 Word。
- 默认采用横向 A4 单页信息图式布局；若内容无法在保证可读性的前提下容纳一页，可扩展为两页，禁止把正文压缩到10磅以下或裁切内容。
- 标题、各级章节和表格文字均为中文；标题使用 Word `Title` 样式，章节使用 `Heading 1`，子章节使用 `Heading 2`，编号必须与 HTML/PDF 一致。
- 图表应以清晰的高分辨率 PNG 或兼容矢量格式嵌入，设置中文替代文本；表格必须有浅灰色边框、清晰表头、合理列宽和单元格内边距。
- 不在标题下添加装饰横线，不使用文本框模拟正文，不留下工具引用标记、占位符、批注或修订痕迹。
- DOCX 必须使用文档能力自带的 `render_docx.py` 渲染为逐页 PNG；以100%视图检查每一页，发现截断、重叠、乱码、图表模糊或异常分页后必须修改并重新渲染。

### PDF规范

- PDF 默认由已经通过视觉检查的最终 DOCX 导出；若独立生成，使用 PDF 能力推荐的 `reportlab` 等可靠工具。
- 页面尺寸、方向、章节顺序、图表、页脚日期和风险提示与 DOCX 一致；字体必须嵌入或使用可稳定显示中文的字体。
- 使用 `pdfinfo` 或等价方式检查文件非空、页数和页面尺寸；使用 `pdftoppm` 将每一页渲染为 PNG，并逐页检查文字、表格、图表、页边距和中文字符。
- 禁止把网页截图直接冒充PDF正文；禁止交付未经渲染检查的PDF。

### HTML规范

- 使用语义化 HTML、响应式布局和打印样式；不得依赖网络请求才能显示核心内容。
- 图表需有中文标题、单位、图例和无障碍说明。打印样式应与 Word/PDF 的信息层级一致。
- 交付前检查无占位符、无内部路径、无工具调用说明，并确认常见桌面宽度和窄屏下无横向溢出。

## 输入

至少取得一个可唯一识别的目标：ETF 场内代码（优先，带交易所后缀）或ETF全称/简称。用户只给名称时，先通过 MQL 上下文检索确认唯一证券代码；若同名或无法唯一确认，停止并要求用户明确标的，禁止猜测。

所有日期以运行当日 `CURRENT_DATE` 为基准；代码、日期、枚举值按字符串传递，不得擅自改写证券、缩放单位或补全未知字段。

## 强制调用顺序

1. 先调用 `Get_MQL_Reference`，核验其 `requiredRuntimeCompatibilityVersion` 与 `Execute_MQL` 描述中的运行时版本。随后调用 `Search_Business_Knowledge`，再调用 `Search_Context`。MQL 工具要求的这三个步骤不得跳过。
2. 在首次 `Search_Business_Knowledge` 中使用完整用户原句；`varieties` 至少包含“基金”，涉及指数时同时包含“指数”；先写2至3条标准化改写，再从原句和改写中提取有业务意义的关键词。
3. 首次 `Search_Context` 一次提交全部已知参数，并原样传入业务知识结果中的全部 `typeCodes`。将目标ETF放入 `searchEntity.words`，将 `RPT_ETF_FUND_SHEETPAPER` 及所需字段放入 `searchIndicator.keys`。只有结果明确缺少必要信息时才补调缺失分区。
4. 使用已确认的完整报表路径、过滤字段和返回字段生成 `ReportBlock` MQL，并调用 `Execute_MQL`。首个执行对象必须是条件接口 `RPT_ETF_FUND_SHEETPAPER`，入参为用户目标ETF的场内代码（带后缀），参数名 `SECUCODE`。
5. 从条件接口读取并缓存所有后续入参，至少包括：基金代码（无后缀）、基金代码（场内后缀）、基金代码（OF后缀）、基金经理代码（现任）、基金公司机构代码、跟踪指数代码、跟踪该指数的标的基金只数、基金成立日、最新报告期、最新净值日期、是否货币基金、是否QDII基金、所属ETF投资范畴-板块编码、投资范畴分类-一级代码 `ETF_TYPE_ONE`。
6. 在条件接口成功且分类明确前，不得调用任何章节接口，不得搜索资讯，不得起草报告。
7. 根据下方“分类与章节路由”确定唯一章节清单。只调用该类型所需接口；可将相互独立且入参已齐备的章节数据并行获取，但每个接口都必须遵守 MQL 的参考检索链。
8. 结构化数据完成后，才可为“投资价值与市场展望”调用 `mx_finance_search_news`。查询必须精确包含目标基金代码、基金简称、关注主题及最近30日范围；只保留同时匹配目标代码或目标名称的内容。
9. 先完成各章节正文，再写“核心投资逻辑”。核心投资逻辑是全文摘要，不是前置猜测。

## MQL报表发现与批量查询

新版接口目录位于 `references/interface_catalog.json`，它由“取数工具整理”和“取数工具应用明细”合并生成。执行报告前必须读取目录中本次分类会用到的接口记录。英文接口名、中文名称、已知路径、入参来源和返回字段共同用于发现报表；任何一项都不能单独作为已确认元数据。

使用 `scripts/etf_one_page.py discovery-plan <条件接口结果.json>` 生成发现计划。禁止把全部接口名一次性塞入一次 `Search_Context`：

1. 条件接口单独检索并执行。
2. 条件接口成功后，按章节检索；每批最多3个业务高度相关的接口，不跨章节混批。
3. 每个接口的主检索短语必须同时包含：英文接口名、中文接口名、目录中的路径提示，以及4至8个最具辨识度的中文返回字段。`searchIndicator.keys` 保留每个接口各自的完整短语，不把多个接口压成一个长字符串。
4. 已知路径只是检索提示。只有 `Search_Context` 当次明确返回的完整报表路径、`reportStandardCodeSupported`、`reportFilterColumns`、`reportFields` 和 `matchedReportFields` 才能用于生成 MQL。
5. 一批中部分接口未发现时，已发现接口照常执行；不得因为一个接口失败而放弃整批，更不得整批降级到资讯搜索。
6. 对“元数据未发现”的单个接口只允许一次定向补检。补检短语使用“中文接口名＋所属章节业务场景＋入参中文名＋关键返回字段”，不更换标的、不改写实际数据查询 `query`。补检仍未发现则记录状态并跳过该接口。
7. 同一接口出现多个候选报表时，按英文接口名精确匹配、中文名匹配、路径提示匹配、关键字段覆盖率依次评分；无法得到唯一最高候选时不得猜测，标记“元数据未发现”。

必须为每个接口维护下列独立状态：`待发现`、`元数据未发现`、`入参缺失`、`前置条件不满足`、`待执行`、`执行成功且有数据`、`执行成功但为空`、`执行失败`。只有“执行成功但为空”可以描述为无数据；“未发现”“未执行”和“失败”不得混称为空。

## 逐接口执行审计与流程锁

开始章节接口检索前，必须用 `scripts/etf_one_page.py audit-init <条件接口结果.json> <审计文件.json>` 建立执行矩阵。审计文件放在当前任务的 `work/` 目录，不写入报告正文。每个计划接口必须有且只有一条记录，并持续记录元数据发现、入参判定、执行尝试、返回行数和失败原因。

字段定义、合法状态转换和命令示例详见 [references/execution_audit_schema.md](references/execution_audit_schema.md)。执行审计时必须读取该文件。

### 覆盖率硬规则

- “元数据已发现”是指当次 `Search_Context` 已明确返回完整报表路径、代码支持方式、过滤列和返回字段。达到该状态且入参齐备、前置条件成立后，接口必须进入`待执行`，随后至少调用一次 `Execute_MQL`。
- 其他接口或同一接口的多 Block 已提供相同数据，不得把该接口标记为已完成，也不得免除独立执行。覆盖只能用于结果交叉校验，不能替代执行。
- `执行成功且有数据`、`执行成功但为空`、`执行失败`均表示已经发生实际执行尝试；`待执行`表示尚未执行。元数据检索成功绝不等于接口执行完成。
- 预算约束只限制相同 query 的重复调用、无效重试和空转，不限制计划内接口的首次执行。不得以“节省调用”“数据已经够用”“报告可以完成”为由跳过首次执行。
- 只要执行矩阵中仍存在一个`待执行`接口，就不得搜索资讯、起草正文或生成交付文件。

### 章节检查点

每完成一个章节的数据采集，必须执行：

```text
python scripts/etf_one_page.py audit-checkpoint <审计文件.json> --chapter "<章节名称>"
```

检查点必须满足该章节全部接口均已进入终态：`元数据未发现`、`入参缺失`、`前置条件不满足`、`执行成功且有数据`、`执行成功但为空`或`执行失败`。出现`待发现`或`待执行`时检查失败，禁止进入下一章节。接口失败不阻断其他独立接口，但必须记录原始错误类别与简明原因。

### 写作前总验收

结构化数据阶段结束后，必须执行：

```text
python scripts/etf_one_page.py audit-finalize <审计文件.json>
```

脚本计算：计划接口数、元数据发现数、应执行接口数、实际执行接口数、成功有数据数、成功为空数、失败数、未发现数、入参缺失数、前置条件不满足数和执行覆盖率。执行覆盖率定义为：

```text
实际执行接口数 ÷ 应执行接口数 × 100%
```

其中“应执行接口”仅指元数据已发现、入参齐备且前置条件成立的接口。写作前执行覆盖率必须为100%，并且未执行接口列表必须为空；否则脚本返回非0，禁止继续生成报告。

### 更新审计状态

每次检索或执行后立即调用 `audit-update`，不得在任务末尾凭记忆补录。至少记录：

- 元数据未发现：`--state 元数据未发现 --reason <原因>`。
- 入参缺失或前置条件不满足：写明缺少字段或不成立条件。
- 元数据确认完毕：`--state 待执行 --metadata-found`，并记录确认后的报表路径。
- 执行完成：分别记录`执行成功且有数据`、`执行成功但为空`或`执行失败`，以及调用次数、返回行数、执行ID或错误类别。

`audit-update`必须校验状态转换，禁止从`待执行`直接改成“元数据未发现”，禁止把失败改成空数据，禁止以“其他接口已覆盖”作为跳过理由。

### 面向用户的交付说明

执行矩阵不进入报告正文，但最终交付消息必须简要报告“应执行接口数、实际执行接口数、执行覆盖率、失败/为空/未发现数量”。如果某章节因所有相关接口均无有效数据而被删除，交付说明只陈述数据状态，不得在研究报告正文暴露工具名、接口路径或调用过程。

### 原接口参数到MQL的转换

目录中的 `SECUCODE`、`ORG_CODE`、日期等是原报表入参规则，不等于可以直接写入 `ReportBlock`：

- 若元数据返回 `reportStandardCodeSupported=true`，证券标的范围使用 `SetCodes(...)`，代码口径严格采用目录指定的场内后缀、OF后缀、无后缀、经理代码或指数代码。
- 其余条件只有在当次元数据的 `reportFilterColumns` 中存在时，才能用确认后的列名写入 `SetReportFilter(...)`。枚举固定值、日期区间、`IN` 条件保持原值和原类型。
- 返回字段仅从 `reportFields` / `matchedReportFields` 中选择，并使用其确认的中文字段名调用 `REPORT_FIELD(...)`。
- `ReportBlock` 禁止使用 `SetParams`，禁止把原接口参数名、接口名或路径猜测成过滤列。
- 入参值缺失时标记“入参缺失”；前置条件不成立时标记“前置条件不满足”。不得用相近代码、当前日期或其他字段代填。

## 章节写作规则

### 核心投资逻辑

最后生成，300字以内。基于已完成且非空章节，用一句话优先概括目标ETF在同类中的定位、核心特质、差异化优势与适用场景；谨慎使用“唯一”“最”等绝对词，不给买卖建议。

### 基金概况

500字以内。子章节依次为：ETF基本信息；管理人与投研实力；跟踪指数核心解析。第三节仅在指数资料存在时生成。数据必须伴随解释，不罗列简历和参数。

### 规模、持有人结构与流动性分析

600字以内。子章节依次为：规模与份额变动趋势；持有人结构；场内交易活跃度；资金流向。严格区分份额与规模，解释趋势、筹码稳定性、成交活跃度与净申赎偏好。

### 业绩与运作特质

非货币ETF 500字以内：阶段收益；跟踪运作效率。结合阶段/年度收益、跟踪偏离、跟踪误差和折溢价分析适配环境。货币ETF 400字以内，围绕七日年化、阶段收益和年度收益，分析利率、信用周期与资金松紧下的特征。

### 风险收益特征

300字以内。使用夏普、年化收益、最大回撤、波动率等已取得指标，说明不同市场环境下的收益风险特征与风格稳定性。无数据则整章省略。

### 投资组合分析

600字以内。股票ETF依次分析申购赎回成分、重仓持股、行业配置；债券ETF依次分析申购赎回成分、重仓债券、券种配置、久期分布；跨境ETF依次分析申购赎回成分、重仓持股、行业配置、地区配置。重点覆盖前五/前十集中度、组合特征、调仓与跟踪误差线索、行业或券种结构、信用/利率/汇率风险；只写数据可支持的结论。

### 同类型ETF比较

400字以内。比较区间收益、风险收益、回撤、波动率、规模及排名，重点说明差异和适用场景。接口无有效结果时必须完全省略。

### 投资价值与市场展望

股票、债券、商品、跨境ETF 600字以内；货币ETF 300字以内。资讯查询格式为“`基金代码 基金简称 的投资价值与市场讨论，最近30日`”。只采信完全对应目标ETF代码或名称的资讯；其他ETF、其他代码或其他品类内容一律忽略。无精确匹配资讯则整章省略。

- 股票ETF：拆解底层逻辑、宏观/政策/产业催化向成分股的传导、估值或景气位置与风险。
- 债券ETF：分析货币政策、资金面、信用环境、利率走势、信用与流动性风险。
- 商品ETF：分析供需、库存、通胀、美元、产业政策、地缘事件与风险。
- 跨境ETF：分析海外宏观与货币政策、人民币汇率、产业景气、地缘事件、全球资金流动与风险。
- 货币ETF：分析市场资金面、短端利率、央行操作、交易所资金松紧、股市成交额分流与风险。

## 图表与版式

图表数量以解释数据为目的，通常12至20个，不为凑数作图。主色为暗红 `#8B1E2D`，辅色为橙色 `#E67E22`；对比项可用中性灰，避免高饱和杂色。

- 纵向数据表：基金概况、同类ETF比较、前十大持仓/债券等适合逐项比较的内容。
- 横向数据表：阶段收益、年度收益、风险指标等适合跨期限比较的内容。
- 折线图：规模、份额、净申赎、收益、跟踪偏离、折溢价、七日年化等时序。
- 柱状图：持有人结构、行业/地区/券种/久期分布、同类排名或集中度。
- 柱线组合图：规模与份额、收益与规模、净申赎与价格等确有共同解释价值且单位清晰的双指标。

每张图表必须有中文标题、时间范围、单位、图例和数据口径；双轴图清楚标注左右轴。禁止三维图、饼图堆叠过多类别、截断坐标制造夸张差异。数据不足或图表不能增加解释力时不生成。

### 按章节选择图表

参考报告的有效信息编排方式，但不复制其配色、文字、结论、页眉页脚或来源话术。图表必须紧邻首次解释它的段落，先呈现图表再给出结论；一张图只回答一个主要问题。

- 基金概况：ETF基本信息、基金经理信息、基金公司规模和产品结构优先用紧凑横向表格；公司产品结构类别较多时可用横向条形图。指数跟踪基金规模按年份使用柱状图，规模占比有连续年份时可叠加折线形成柱线组合图。
- 规模与份额：日频或月频规模、份额使用双折线或柱线组合图；两者单位不同时必须双轴。数据点过密时按周末或月末抽样，保留首末值和异常峰值。
- 持有人结构：报告期较少时使用分组柱状图，同时展示机构、个人及必要时员工占比；户数可作为折线叠加，但不得与份额占比共用同一轴。
- 流动性：不同期限的日均成交额/成交量使用横向数据表；连续行情使用成交额柱状图叠加换手率或收盘价折线。不存在连续时序时不得伪造趋势图。
- 资金流向：净申赎份额或规模使用以零轴为基准的正负柱状图；场内流通份额可叠加折线。正值暗红、负值橙色或中性灰，并明确正负含义。
- 业绩：近一年净值或累计回报使用折线图；阶段回报、年度回报优先横向表格，期限足够多时用柱状图。基金、基准和宽基对比只在日期口径一致时同图展示。
- 跟踪效率：日跟踪偏离度使用围绕零轴的折线图；年化跟踪误差用折线图；溢折率用折线图并叠加均值和一倍/二倍标准差参考线。
- 风险收益：指标数量少时用横向表格，不使用雷达图；与同类均值/中位数可比时可用分组柱状图。
- 投资组合：前十大持仓、申赎成分和重仓债券优先纵向表格或水平条形图；行业、地区、券种和久期分布使用按占比降序的水平条形图。类别超过10个时展示前8至10项并将其余合并为“其他”，仅在原始数据可准确汇总时执行。
- 同类比较：使用纵向对比表呈现目标、均值、中位数和排名；仅当量纲一致时增加分组柱状图。收益、回撤、波动率、规模不得放在同一数值轴。

版式密度参考“一段结论＋一张核心图/表”的节奏。单个子章节通常不超过2张图表；整份报告通常12至20个图表或数据表，其中至少包含2张趋势图和2张结构/比较表，但数据不足时以真实性优先，不为满足数量补图。

## 超时与重复调用

调用脚本使用 `scripts/etf_one_page.py` 的执行保护。单次调用最长等待1200秒。相同 `query` 在一次报告任务中累计最多调用2次；仅当命令正常结束且结果明确标记为可重试失败时，首次失败后等待30秒再进行唯一一次重试。90秒退避位仅作为兼容配置保留，受“累计最多2次”上限约束，不得触发第三次调用。

上述预算只限制同一 query 的重试和无效空转，不限制计划接口的首次执行数量。一个接口执行失败不免除后续独立接口的首次执行；只有下述超时、命令中断或非0退出码触发的全局停止规则可以中止本轮。

若命令超时、被中断或返回非0退出码，立即停止本轮报告生成，禁止后台执行，禁止改写 `query`，禁止更换标的重试，禁止静默降级到其他数据源。输出固定失败话术：

> 数据查询失败，本轮已停止。未改写查询、未更换标的，也未在后台继续执行。请稍后使用同一请求重新发起。

MCP 直接调用同样遵守“同一 query 累计不超过2次”的上限；不得因报错反复改写同义 query 规避计数。
