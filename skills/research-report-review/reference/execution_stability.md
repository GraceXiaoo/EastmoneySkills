# 分阶段执行、检查点与防循环

## 1. 真实预算与禁止事项

当前平台单任务最大执行轮次为 100 次，这是明确的运行环境约束。不得自行生成其他“约 N 次工具后必须交卷”“时间有限”“积分不足”等限制，也不得据此减少覆盖、绕过 MQL、提前使用兜底数据源或把未完成结果标为完整。

任务开始时在 `run_manifest.json` 初始化执行预算；每个实质执行轮次前运行 `scripts/run_manifest.py --manifest <path> budget --increment 1 --limit 100 --checkpoint-at 85`。达到 85 次后立即原子保存五个阶段工件、服务状态、未完成对象和下一步动作，停止发起新远程调用，向用户汇报已完成/未完成内容并询问是否继续。用户确认继续后由新一轮任务从检查点恢复；不得为了赶在第 100 次前删除对象、跳过指标或生成虚假完整结果。已 `PASS` 的对象续跑时直接复用，不重复消耗轮次。

真实资源限制出现时，先原子保存当前阶段文件和未完成清单，再如实报告状态。不得用静态值、错误日期、近似口径或不完整 JSON 填补缺口。

## 2. 渐进读取

不得在任务开始时加载全部参考文件：

1. 摄取与普查：只读 `pdf_layout_api.md`、`ingestion_rules.md`。
2. 指标分类与映射：再读 `indicator_inventory_template.md`、`mql_execution_protocol.md`。
3. 工作簿生成：再读 `workbook_spec.md`。
4. 数据差异归因：仅需要时读 `tolerance_rules.md`、`unmatched_attribution.md`。
5. 预测复盘或最终报告：仅用户选择对应模式时读预测或报告模板。

工具的巨大原始返回按 [数据执行协议](mql_execution_protocol.md) 的 ①「原响应」层规则**原样**落盘（不做格式改写），只在上下文保留路径、记录数、状态和下一步；不得反复粘贴完整原始响应，也不得改写为 HTML、Excel 或其它交付文件。

## 3. 阶段工件

同一任务目录只维护以下权威工件：

| 阶段 | 文件 | 最低内容 |
|---|---|---|
| 1 | `01_census.json` | `guide`、页面清单、纳入/排除表图清单、`excluded_tables` |
| 2 | `02_source_evidence.json` | `snapshots`、`chart_snapshots`、`chart_data`、逐对象视觉验收状态 |
| 3 | `03_mapping_plan.json` | 每个指标的标准指标候选、报表候选及选择理由，来源/查询时间形态、实体/标准代码或板块体系、目标行列轴、状态、标准失败类别、失败证据和兜底准入 |
| 4 | `04_query_results.json` | `workpapers`、`verification`、`execution_log` 及真实原始返回引用 |
| 5 | `05_workbook_input.json` | 构建器唯一输入，由脚本合并阶段工件产生 |

任务目录同时维护 `run_manifest.json`：记录源 PDF 指纹、Skill 版本、各阶段输入指纹、对象状态、操作键、执行 ID、结果文件路径和更新时间。平台或会话重启后先读取 manifest；指纹未变化且状态为 `PASS` 的解析、检索、MQL 执行和视觉验收全部复用。

`run_manifest.json` 顶层另须维护两个清单字段，与交付矩阵、外部受阻清单构成同一事实的三处载体，逐条对应、不得只写其一：

- `refresh_capability`：`refreshable_anchors` 逐锚点登记 `mapping_id`、`source_id`、`script_sha256`、`execution_run_id`、脚本与结果路径、`mapping_status`；`non_refreshable_items` 逐项登记无法进入锚点的内容及原因；`online_refresh_verified` 仅在加载项实机刷新通过后置真，离线逻辑通过不得置真。
- `external_blockers`：按 `id` / `dependency` / `status` / `impact` 逐条登记外部受阻项，ID 与外部依赖阻塞清单保持一致。

上述字段由任务回填或阶段脚本维护；阶段脚本通过 `--manifest` 参数记录操作，记录属尽力而为，落盘失败不得阻断主构建流程。

使用 `scripts/run_manifest.py` 原子记录和检查操作。远程调用前先运行 `check`；返回 `reusable=true` 时直接读取已记录结果，完成调用后用 `record --status PASS --result-path ... --execution-id ...` 落盘。`check` 返回不可复用才执行远程调用。

每次工具调用后，只更新受影响的对象并原子写回阶段文件。状态只允许 `TODO → IN_PROGRESS → PASS|BLOCKED`。除非源 PDF、接口响应或用户要求变化，`PASS` 对象不得回退或重新执行。

`03_mapping_plan.json` 是执行计划，不直接并入工作簿输入。使用 `scripts/merge_workbook_phases.py` 合并阶段 1、2、4 和预测对象；不得另建第二个完整 JSON 构建脚本，也不得在自然语言中重新手工拼装全部数据。

每个阶段在进入下一阶段前先完成本阶段 schema 预检。`02_source_evidence.json` 先经 `scripts/prepare_workbook_phases.py normalize-evidence` 生成机械字段；不得等到最终合并后再用校验器逐项发现行标签、数值令牌、轴枚举和期间错误。`05_workbook_input.json` 是只读派生产物：发现完整校验错误时，根据错误字段回写拥有该字段的阶段文件，再重新合并；禁止直接补丁修改派生文件。

阶段工件必须在顶层声明 `schema_version`（当前为 `1`）。缺失该字段的工件按旧 schema（`LEGACY`）处理，由 `scripts/merge_workbook_phases.py` 显式迁移并逐工件写入产物 `migration_log`，不得当作当前 schema 静默合并；声明未知或更高版本时合并器直接报错拒绝，不得降级、猜测迁移或在无迁移证据的情况下继续。生成端（`scripts/prepare_workbook_phases.py` 的 `from-layout` 与 `normalize-evidence`）输出的 census/evidence 工件必须自带 `schema_version: 1`，因此缺失版本号的工件仅应存在于版本化机制建立之前的历史产物；该生成端要求由 `tests/test_phase_schema_version_1019.py` 回归覆盖。

旧 schema 工件的 `FULL` 结论不得继承为新语义 `FULL`：迁移时 `workpapers[*].mapping_status` 与 `chart_data[*].mql_mapping_status` 一律降级为 `PARTIAL`，并在 `migration_log` 逐条记录 `from`/`to`/`reason`（`LEGACY_SCHEMA_FULL_NOT_REVERIFIED`）作为待重验证据；可无歧义推导的说明字段（`mapping_note` / `mql_mapping_note`）自动补写，新语义要求但旧工件无法推导的证据字段（如 CHART 的 `omitted_metrics`）不得编造，直接阻断合并并要求按当前 schema 重新检索验证。

## 4. 调用去重和重试

调用前生成由“工具名 + 规范化参数 + 目标对象 ID”组成的操作键，并在阶段文件记录结果：

- 相同操作键已成功：直接复用，禁止再次调用。
- 失败但参数、候选路径和方法均未变化：禁止原样重试。
- 工具返回 `error` 且输出为空：若相同操作曾成功则复用成功结果；否则只允许一次不同方法的诊断，仍无增量则将该对象标为 `BLOCKED`。
- 单个指标或对象累计最多 3 次修正尝试；每次必须记录新增信息。达到上限后停止该对象，不停止其他对象。
- 修正重试达到上限本身只会把对象标为 `BLOCKED`，不会把实体代码、板块集合、日期、语法、参数或路径错误改写成“无数据”或服务故障；实际服务故障的兜底准入另按数据执行协议处理。恢复执行时先读取标准失败类别；只有方法或候选发生变化才可继续。
- “无增量”严格指连续两次尝试均没有新的候选路径、返回记录、错误详情、文件变化或状态变化；无增量时阻断当前对象，不得虚构全局预算。

## 5. 生成层熔断

用户可见进度只写“已完成工件、当前动作、阻塞项”，不写反复自我指令。出现以下任一情况时立即停止继续生成计划文本：

- 相同句子或段落连续出现两次；
- 相同“接下来我要……”连续出现两次且中间没有工具结果；
- 同一阶段被第三次宣布开始；
- 前一回复因重复或截断结束。

熔断后执行固定恢复动作：读取五个阶段文件 → 找到首个 `TODO/IN_PROGRESS` 对象 → 检查操作键历史 → 执行一个具体工具动作或把对象标为 `BLOCKED`。不得从上一段自然语言恢复，不得再次道歉后重复整套计划。

## 5.1 外部服务调用保护与按服务熔断

PDF 版面解析、Vision、MQL 检索/执行、妙想数据服务、远程文件转换等都属于可能阻塞的外部服务。保护粒度是一个有明确业务边界的批次，而不是批次内每个正常请求。典型批次为“一次 PDF 解析”“同页截图的统一 Vision 验收”“一个指标族的检索”或“一个可复用 MQL 执行组”。批次开始前使用：

`scripts/service_guard.py --state <task>/service_state.json start --service <service> --object-id <source_id> --operation <operation> --method <method>`

该命令会在远程调用前原子写入 `PENDING` 并增加尝试次数，因此调用挂起或平台重启后仍可识别未完成尝试。工具返回后立即用 `finish` 记录 `PASS`、`INCOMPLETE`、`TIMEOUT`、`PARSE_FAILED`、`RATE_LIMIT`、`AUTH_INVALID` 或 `ERROR`。

- 服务名称必须稳定且细分到可独立判断健康状态的端点，例如 `pdf_layout`、`vision`、`mql_reference`、`mql_search`、`mql_execute`、`mx_data`、`remote_convert`。不得把所有外部调用统称为 `remote`，也不得为了绕过熔断临时改名。
- 计数键为“服务 + 批次对象 + 操作”。同一批次最多 3 次；改变同义提示词、等待、重启会话或改写无实质差异的参数不会重置计数。不得为了记录状态而给批次内每次成功调用额外增加一对 shell 工具调用；可在阶段文件中一次结算整批对象。
- 运行环境支持超时参数时必须设置有界超时，并按服务/API 的正常响应特征选择，不得用一个过短的全局秒数误杀所有调用；环境不支持时沿用工具原生超时。任何情况下不得通过 `sleep` 延长等待或构造轮询死循环。
- 同一服务连续 2 次服务型失败（`TIMEOUT`、`PARSE_FAILED`、`RATE_LIMIT`、`ERROR`、恢复时发现遗留 `PENDING` 而记为 `ABANDONED`）立即只打开该服务的熔断器。一个服务熔断不得阻止其他服务继续，也不得把服务异常误写成指标无数据、PDF 无图表或 MQL 不支持。
- `AUTH_INVALID` 是不可重试的配置/凭据失败，首次出现即打开对应服务熔断器，不占用后续两次尝试；只有重新注入有效凭据后才允许显式重置。不同服务即使使用同名账户凭据，也必须以各自调用响应判断，不得用另一个服务成功来推定本服务鉴权有效。
- 熔断后禁止对该服务使用 sleep、空请求、同义提示词、其他对象或无业务意义的小请求做健康探测。立即原子保存阶段工件；MQL明确故障可按数据执行协议自动兜底受影响项，非明确终态或其他服务仍保存阻塞。继续文件整理、已有结果装配以及独立阶段。
- 若缺失服务只影响部分对象，允许生成明确标记的部分交付；若完整性门禁依赖该服务，则以“被 `<service>` 服务阻塞”结束，不得无限等待、降级伪装成功或让整项任务无输出。
- 只有新任务、用户明确要求恢复，或平台提供服务已恢复的外部证据后，才可对对应服务执行 `service_guard.py reset --service <service>`；重置一个服务不得清除其他服务历史，已 `PASS` 对象不得重做。
- 续跑时若某操作最后一条记录仍为 `PENDING`，保护器会先将其结算为 `ABANDONED` 并计入服务失败，再判断熔断和本次是否允许；不得直接再发起一次而把挂起调用隐去。

## 6. 数据源和完整性不受效率措辞影响

MQL 的语法、参数、代码或日期错误必须按数据执行协议修正；“需要高效”“结果很多”“上下文较长”都不是切换 `mx-ds-mcp` 的理由。只有完成的MQL检索/查询确认缺指标、缺结果，或真实调用已返回明确服务故障并满足数据执行协议准入时，才能自动兜底受影响缺失项；未完成、中断或ABANDONED本身不能证明故障。

不能满足完整门禁时，交付状态必须是“部分完成”或“阻塞”，并列出已完成与未完成对象；不得生成所谓“核心数据简化版”后声称完整。

## 7. 性能目标与执行批次

用户要求兼顾首次执行速度。对约 4 页、10 个左右表图的常见个股研报，以 20–30 分钟完成为工程目标；指标元数据缓存命中、接口响应正常时争取 10–20 分钟。该目标用于减少重复工作，不允许减少字段、期间或视觉验收。

1. 普查完成后一次生成全表 mapping plan；只提交研报实际出现且缓存未命中的字段。同一公司相同财务指标族和报告期集合只做一次业务知识检索、一次批量上下文检索；不得为建立“完整指标库”而扩大本次检索。
2. MQL 按“实体 + 指标族 + 完整期间集合 + 参数口径”批量执行。财务指标先使用原生多报告期或候选确认的财务时序能力，避免把每个报告期拆成独立远程调用；确不支持时才分期并在同一脚本中合并。多个来源表需要相同执行结果时复用原始结果引用，不重复远程执行；Excel 锚点仍生成各自需要的同形脚本。
3. 禁止在对话中展开大型矩阵或反复读取完整日志；按 [数据执行协议](mql_execution_protocol.md) ① 层原样落盘（不做格式改写），只读取 schema、形状、哈希、错误路径和必要样本。
4. 正常路径为：证据规范化一次 → 合并一次 → `preflight_workbook_input.py` 一次性列出机械错误并调用与构建器相同的最终校验 → 必要时统一修正来源阶段并最多再预检一次 → 完整 `--validate-only` 一次 → 生成一次。预检第二次仍失败时把错误清单落盘并标记 `WORKBOOK_SCHEMA_BLOCKED`；禁止通过改变 shell 包装、直接调用 Python 函数或改写等价参数绕过去。校验、合并和构建命令不得接 `head/tail` 等会掩盖前序退出码的管道；必须直接检查命令退出码。最终校验器不是 schema 探索工具。
5. Vision 按页面或相同版式组成联系表批量验收，一次返回每个 `object_id` 的结构化结论；逐对象登记结果不等于逐对象远程调用。
6. 首次执行慢于目标时，在报告中按 PDF 解析、视觉验收、检索、MQL、构建分别记录耗时和调用数，用于定位瓶颈；各外部服务的超时、重试、熔断和阻塞耗时分别列示，不得用“任务复杂”代替阶段数据。
7. `通过MQL工具链获取结构化数据` 或参考工具的完整响应按 [数据执行协议](mql_execution_protocol.md) ① 层原样只保存一次（不做格式改写）；立即用 `mql_context_index.py` 生成紧凑候选索引。后续检索只读取索引中的命中路径和必要上下文，不得对同一大响应连续运行多个临时 shell 过滤命令。
