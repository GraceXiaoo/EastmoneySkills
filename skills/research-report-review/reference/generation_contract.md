# 底稿生成契约

本契约在任何 MQL 检索或脚本生成之前建立。目标是直接生成完整、可读、与原文同形的底稿，而不是先生成最小可运行结果再依赖校验补救。

## G0：可刷新执行单元

每个最终锚点先固定最终 MQL，再执行、验收并原样写入批注。执行脚本、workpaper `mql_script` 与 Excel 批注只允许有一个字符串来源，并以 SHA-256 绑定对应执行日志。预检解析选中 Block 的输出别名，核对实际返回表头、单位契约及转换表达式；不能用综合查询的裁切矩阵证明另一段脚本可刷新。

溢出区域以该最终脚本真实返回矩阵应用 orientation 后的形状规划。跨市场可比公司按市场拆分执行，所有段使用统一字段顺序、币种元数据和研报实体输出顺序。

## G1：视觉对象与截图计划

1. 从全页普查中合并两类对象：所有 `classType=image` 块，以及标题/编号/来源行表明其为图表的表格块。
2. 每个视觉对象都先产生原文截图，再处理结构化结果。接口将同一对象识别为表格时，建立 `chart_id ↔ parsed_table_ids` 配对；解析表只是截图后的证据，不代替截图。
3. `visual_object_count` 在查询前固定，必须等于最终 `chart_snapshots` 数。对象不得因“已有接口表格”、“为内容型”或“不进入 MQL”而省略截图。

## G2：来源字段和原文布局契约

对每张纳入表格，在查询前写入：

- `queryable_fields`：按原文顺序列出所有可结构化查询的指标、序列或实体字段；
- `source_row_axis` 和 `source_column_axis`：从 PDF 表头、行标签和视觉布局确定；
- `source_semantic_type`：由原文结构确定的语义类型；
- `source_periods`：按原文顺序列出全部 `ACTUAL` 报告期；
- `layout_contract_reason`：简要记录判定根据。

目标底稿默认优先保持来源布局。例如原文为“指标纵向、日期横向”，则底稿的可读布局优先为 `METRIC × DATE`，MQL 原始返回是日期行时可应用 orientation 转为来源布局。但版式不是验收条件：底稿按本次实际成功结果输出，允许合约长表、品种矩阵、分市场表、分部表和多锚点组合，不要求仅靠转置恢复原表；表头、标准简称或行列排布与原文不同，本身不得把结果判为 `PARTIAL`，也不得据此删除成功结果。财务来源仍固定 `FINANCIAL_METRIC × REPORTING_PERIOD`。例外是非财务截面来源只能部分映射到真实执行成功的 `EdbBlock` 时序：不得为伪造同形截面而删除成功结果，应以 `PARTIAL/SUCCESS` 输出 `DATE × SERIES`，完整记录来源字段覆盖与省略原因，并把每个 EDB 锚点隔离到独立 `21_EDB_NNN` Sheet。

### 财务表不可降级分类

出现以下任一结构证据时，来源快照必须标为 `FINANCIAL_STATEMENT` 或 `FINANCIAL_METRICS`：

- 表名属于资产负债表、利润/损益表、现金流量表、财务摘要、主要财务比率或每股指标；
- 行轴为财务科目且列头包含报告期；
- 两个及以上 `ACTUAL/FORECAST` 期间列对应同一组财务科目。

财务来源固定使用 `FINANCIAL_METRIC × REPORTING_PERIOD`。查询规划和工作底稿只能继承该语义与轴，不能为了使用单期 `CrossSectionBlock`、减少字段或通过校验而改为 `CROSS_SECTION_TABLE` 或 `ENTITY × METRIC`。唯一例外是财务来源拆出的非财务形态锚点（如估值截面）登记 `source_semantic_type=OTHER`，其适用条件以 `workbook_spec.md`「财务来源 OTHER 锚点豁免」为唯一权威，本节不重列。

`source_periods` 只收集原表 `ACTUAL` 期间，分析师独有预测列继续进入预测框架。若财务表有 2024A、2025A，两期都必须进入查询计划。整张财报表格（科目 × 报告期全覆盖）先按整表报表路径直取；仅当报表路径不可用或按用户指定指标口径取数时，再依据候选元数据选择能一次返回全部报告期的标准指标形态；只有候选不支持原生多期或真实执行无数据时，才按期间分别执行指标查询并在同一 MQL 中合并。结果必须仍是一个可刷新的 `FINANCIAL_METRIC × REPORTING_PERIOD` 数据块。

**本节是 `financial_query_mode` 的唯一权威优先级链**；`mql_execution_protocol.md`、`workbook_spec.md`、`SKILL.md` 只引用本节，不再各自重列一套顺序。财务查询方式记录为 `financial_query_mode`，按以下优先级选择：

1. `REPORT_FULL_TABLE`：整篇财报表格优先报表路径整表直取（参考 `mql_templates/` 对应科目模板），只需 `report_selection_reason`，不要求先证明指标路径失败；
2. `FINANCIAL_TIME_SERIES`：报表口径不可用或按用户指定指标口径取数，且候选元数据明确支持财务报告期时序时，用单一 `TimeSeriesBlock + SetWindow` 一次返回全部目标报告期；
3. `NATIVE_MULTI_PERIOD`：没有适用时序候选时，标准指标原生接受报告期范围/序列或一次返回全部目标报告期；
4. `PERIOD_BLOCK_MERGE`：前两种不可用时，按报告期分段查询标准指标并在 MQL 内合并；
5. `REPORT_FALLBACK`：仅用于个别科目/单点指标兜底，标准指标路径（上述 2–4）有结构化失败证据后才允许使用报表。

个别财务指标或科目（单点补充、财务比率、估值、图表序列，或整表中少量缺失科目）不适用整表直取，优先检索标准指标路径；指标与报表都能返回目标值时选择指标。

报告期序列不同于证券日频走势。不得仅看到多个报告期就假定指标支持 `TimeSeriesBlock`；必须先检索本次 `通过MQL工具链获取结构化数据` 的参数模式和时间形态。但不得因为时序检索不充分就直接生成多个单期锚点：有时序候选时必须先真实执行单一时序块；没有候选或有效执行无数据时才进入指标原生多期或按期合并。`REPORT_MATRIX` 是最终工作底稿结果形态，不等同于底层查询一定使用 `ReportBlock`。

## G2.5：时间序列窗口策略

时序来源必须同时保留两套日期事实，不得互相覆盖：`source_start_date`/`source_end_date` 保留原图事实区间，`query_start_date`/`query_end_date` 另存本次查询窗口。

应用层记录 `window_policy`，只作为生成期元数据，不写成未确认的 MQL 参数：

- `SOURCE_FIXED`（默认）：保留原图事实窗口；
- `LATEST_1000_TRADING_DAYS`：以「已确认最新交易日」为闭区间终点，取含终点的最近 1000 个交易日。起点不得由自然日历推算，必须来自调用方确认的交易日历；实际有效观测不足 1000 时如实截断并标注。原生滚动起点未获验证，只交付「生成时最近 1000 交易日固定窗口」，`rolling_implemented=false`，不得用固定起点加 `N()` 冒充滚动，也不得发明 `GetTradingDate` 等未确认函数；
- `EDB_FIXED_FREQUENCY`：宏观 EDB 按频率桶处理，不套期货交易日历。

同一时序窗口只对应一个交易市场；跨交易所必须按各自交易日历拆块、分别生成锚点。可选 `{市场类型}`（`SetWindow` 已确认参数）只用于普通时序，取值必须是已确认的交易市场枚举；`_s` 报告期时序只用季或年且不写 `{市场类型}`。可选 `{预加载周期}` 为非负整数字面量，仅当用户明确要求额外历史期数时生成，且正式查询期数与额外期数合计不得超过 1000。

## G3：可读语义名称计划

任何以代码、ID、内部路径或序列键定位的对象，必须在生成查询前建立 `display_label_map[{key,display_name,kind}]`。`kind` 根据对象真实类型填写，不限于证券、股票、指数、行业、利率、债券、基金、商品、期货、外汇、宏观指标或其他数据序列。

生成原则：

1. 底稿同时保留技术键和人类可读名称；技术键用于溯源，可读名称用于展示。
2. 优先在同一 MQL 块中输出标准简称/名称指标。若该品种无名称指标，使用已解析并经候选元数据确认的标准名称输出列；不得凭经验改写名称。
3. 原文名称与数据库标准名不同时，保留两者的映射；工作表优先显示原文名称，执行日志保留标准名与代码。
4. 单独输出 `EM_CODE`、板块 ID、EDB ID 或类似技术键不是合格的底稿展示。

实体为行时，MQL 输出至少包含“代码/键 + 简称/名称 + 数值字段”。实体为列或时序为宽表时，每个序列列头必须是可读名称，代码映射保留在 JSON/日志中。

期间列同样纳入 `display_label_map`：当结果矩阵的期间表头（Choice 实际返回的取数标签，如 `2025-12-31`、`2025年报`）与研报期间标签（如 `2025A`）逐列不同时，必须逐列补 `kind=REPORTING_PERIOD` 条目，`key` = 取数标签（溯源用），`display_name` = 研报期间标签（契约与展示口径用）。`column_axis_labels`、`covered_periods` 一律保留研报标签，不得为迎合取数标签而被改写，也不得改写 `last_result`。期间 `display_name` 必须是可识别的期间记号，行标签的可读性约束不适用于期间条目。逐列一致时无需期间条目。权威定义见 `workbook_spec.md`。报表脚本公开声明的 `{报告期}` 列属于结构键（计入结果表头与期间映射 `key`，不计入 `script_output_fields`/`covered_fields`/`unit_contracts` 比对），口径以 `workbook_spec.md`「声明式报告期结构键」为唯一权威。

## G4：来源级完整覆盖计划

在检索前，为 `queryable_fields` 每项创建候选位，批量搜索全部字段，不得先挑选少数“代表性指标”。同一来源可以由多个锚点分别承担不同字段/期间；每个锚点只声明自己本次取得的目标单元：

- `source_fields`：本锚点本次计划查询的目标字段，必须属于快照 `queryable_fields`；
- `covered_fields`：本锚点本次成功检索且真实执行的字段；
- `omitted_fields[{field,reason,evidence_ids}]`：本锚点内经全量尝试仍终止失败的字段及其结构化证据。

锚点内三者必须不重不漏；`FULL` 仅在该锚点覆盖其全部目标字段时成立。`PARTIAL` 是完成全量尝试后的结果，不是允许提前停在少数成功指标的快捷方式。

来源级覆盖汇总（取代「与快照同形」判定）：设 `E`=来源计划目标单元集（快照 `queryable_fields`、全部 `ACTUAL` 期间），`S = ∪各锚点 covered`，`O = ∪各锚点 omitted`，要求 `S ⊆ E`、`O ⊆ E`、`S ∩ O = ∅`、`S ∪ O = E`。真实缺失在来源汇总层统一计算，已在锚点 B 成功的字段不得写成锚点 A 的 `omitted_fields`。

对含报告期的表同时生成：

- `source_periods`：本锚点本次计划覆盖的 `ACTUAL` 期间，必须属于快照期间集合；
- `covered_periods`：真实执行结果中实际出现的期间；
- `omitted_periods[{period,reason,evidence_ids}]`：经过检索或执行仍终止失败的期间。

期间同样按锚点声明、按来源汇总，不重不漏。`covered_periods` 与应用 orientation 后的结果期间列一一对应；取数标签与研报标签不同时，用 `display_label_map{kind=REPORTING_PERIOD}` 逐列记录对应关系，`column_axis_labels`/`covered_periods` 保留研报标签。只有自由文本理由、没有执行证据的期间不得省略。

## G5：查询与底稿生成

1. 按 G2 的目标轴选择数据组织和 orientation。
2. 财务来源含连续报告期时，先检索同口径 `indicatorTimeShape=time_series` 候选；命中后用 `TimeSeriesBlock + SetWindow` 覆盖全部来源期间，年度用“年”、季度用“季”，不写交易市场。当前运行时返回的 `_s` 只能作为该候选的完整路径证据，不能由名称推断或自行追加。
3. 按 G3 把可读名称字段纳入脚本输出，再执行 MQL。
4. 按 G4 组装全部成功指标；不同市场、品种或路径需拆段时，各段使用相同的展示列契约，再按来源顺序合并。
5. 先用真实 `raw_result` 验收可读名称、字段覆盖、原文布局和单位，再生成 `last_result/cached_table`。
6. 上述任一契约未满足时回到检索/生成阶段修正，不得依赖最终校验器“先通过再说”。

## G6：一次生成与复用

1. 先完成全表的字段、期间、语义和实体计划，再按“实体 + 指标族 + 完整期间集合 + 参数口径”去重和批量检索；不得逐表重复搜索相同财务指标。
2. 同一真实执行块可为多个来源表提供核验证据，但每个 Excel 锚点的脚本必须输出该锚点目标单元所需的结果；同一来源的多个锚点按 G4 的来源级覆盖汇总共同组成完整覆盖。
3. 每次成功检索和执行立即写入阶段工件及 `run_manifest.json`，记录输入指纹、状态、执行 ID、结果路径和完成时间。重启后仅重做指纹变化或未完成的项。
4. 阶段文件先做本阶段轻量校验；全部通过后只合并一次并运行一次完整校验。完整校验失败时按字段路径回写其所属阶段，不直接修改 `05_workbook_input.json`，也不反复全量 merge。
