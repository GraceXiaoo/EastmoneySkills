# 章节文字描述 · 资讯检索取数规范（非 MQL 通道）

> 本 skill 中**所有 9 个章节的「文字描述部分」**统一由**资讯检索通道**供数；
> 章节 3-8 的**表格与图表**仍一律走 MQL（见 `MQL-取数规程.md`）。
>
> 通道边界是硬约束：
> - **不得**用本通道取结构化财务/主营/客户/供应商表（那是 MQL 的职责）；
> - **不得**用 MQL 或模型自有知识替代本通道去写文字描述；
> - **不得**把检索到的研报机构名、评级、目标价写入报告正文（研报内容只可提取基本面事实）。
>
> 章节 2、9 无表格数据，其**全部内容**来自本通道（场景 2 / 场景 9）。

## 1. 通道定义

| 项 | 值 |
|---|---|
| 工具 | 妙想 MCP 工具 `mx_finance_search`（基于东方财富数据库，检索公告、研报、财经新闻） |
| 调用方式 | 本会话 Agent 直接调用工具，**不支持脚本侧直连**；脚本 `news_api.py` 只做结果归一化。11 个场景**相互独立、彼此无依赖** → 按 **§10.1 分 3 批并发提交（每批 3–4 个）**，**不得逐个串行** |
| 入参 | 自然语言 `query`（句式见 §2；公司名称为唯一变量，时间范围经 query 语义表达） |
| 出参 | 文本条目列表：`标题` / `片段代码` / `发布时间` / `链接`（可选）/ `摘要` / 溯源标记 `[source:N]` |
| 失败处理 | 单场景返回为空或工具报错 → 按 §9 降级，不无限重试 |

> **入参唯一（硬约束）**：本通道**只接受自然语言 `query`**，**无分页、无类型、无时间入参**。
> 历史版本文档中出现过的 `size` / `timeSupSize` / `enforceSearchType` / `childSearchType` / `informationType`
> **均为已废止参数，任何文件（含 `prompts/*.md`、`agents/*.yaml`）都不得再写入**：
> 来源类型改由 §2「来源类型（query 语义）」列表达，返回条数不设上限、由 §6 加工 4 步收敛，
> 时间范围一律按 §4 由系统日现算并在 `news_api.py` 侧对 `showTime` 兜底。

## 4. 时间窗口径

窗口 = **系统日往前推 N 个自然月**，即 `[系统日 − N 个月, 系统日]`；起点当天写 `00:00:00`，终点当天写 `23:59:59`。

| 档位 | N（自然月） | 适用场景 | 例（系统日 = `2026-09-23`） |
|---|---|---|---|
| 1 个月 | 1 | `1` | `2026-08-23 00:00:00` ~ `2026-09-23 23:59:59` |
| 6 个月 | 6 | `2` `3.1` `3.2` `4` `5.1` `5.2` `6` `7` `8` `9` | `2026-03-23 00:00:00` ~ `2026-09-23 23:59:59` |

- 日历月回退遇月末不足时按该月最后一天收敛（`2026-03-31` 回退 1 个月 → `2026-02-28`）。
- 窗口一律由系统日现算，**不得**复用上一轮运行结果、不得手写死日期。
- 窗口用于 `showTime` 兜底校验与 `window` 字段展示；`mx_finance_search` 无时间入参，召回依赖 `query` 语义 + 本窗口兜底。
- 仅在复现/回溯时才允许用 `--start` / `--end` 覆盖窗口。

## 5. 返回条目与落盘契约

`mx_finance_search` 每条返回含：`标题`、`片段代码`、`发布时间`（`YYYY-MM-DD HH:MM:SS`）、`链接`（部分条目无）、`摘要`，并带溯源标记 `[source:N]`。

Agent 在每次调用后，把返回条目结构化为 `raw/{scene}.json` 落盘（供 `news_api.py` 归一化）：

```json
{
  "query": "【宁德时代】近况跟踪",
  "company": "宁德时代",
  "items": [
    {
      "showTime": "2026-09-23 12:25:22",
      "title": "资讯标题",
      "chunk": "资讯正文摘要/关键事实",
      "source": "公告 / 研报 / 媒体名",
      "link": "https://pdf.dfcfw.com/...",
      "source_marker": "[source:1]"
    }
  ]
}
```

| 字段 | 是否取用 | 说明 |
|---|---|---|
| `showTime` | **取用** | 资讯时间（返回的 `发布时间`），格式 `YYYY-MM-DD HH:MM:SS`。**场景 1 时间列的唯一合法来源** |
| `chunk` | **取用** | 资讯正文片段（返回的 `摘要`，含事件主体、金额、数量、时间节点等事实信息）。**全部场景文字描述的唯一事实来源** |
| `title` | 辅助 | 资讯标题（返回的 `标题`），用于同源去重，不进入报告正文 |
| `source` | 辅助 | 来源（公告 / 研报 / 媒体），用于来源可信度分级与溯源展示 |
| `link` | 辅助 | 原文链接（返回的 `链接`，无则留空），用于 hover+click 溯源跳转 |
| `source_marker` | 辅助 | 溯源标记（返回的 `[source:N]`），用于溯源展示 |

> 场景 `1` 取 `showTime` + `chunk`；场景 `2`–`9` 只取 `chunk`（拼接为文字描述输入）——
> 它们的文字描述不设时间列，无需 `showTime`，但**仍按 `showTime` 倒序拼接**，
> 以保证较新的事实先进入上下文。

## 6. 结果加工（取数 → 章节文字描述输入的 4 步）

1. **窗口兜底校验**：剔除 `showTime` 缺失、或落在 `[起始日, 结束日]` 之外的条目（查询时已用 query 语义限定时间，此处仅兜底）。`chunk` 为空的条目一并剔除。
2. **同源去重**（严格两遍，顺序不可颠倒）：
   - 同一 `title` 只保留 `chunk` **最长**的一条，保证同一篇资讯只贡献一次；
   - 第一遍存活结果中 `chunk` 完全一致的条目再去重，只保留召回顺序最靠前（来源权威度最高）的 1 条。
3. **排序**：按 `showTime` **倒序**（最新在前）。
4. **chunk 噪声清洗**（在提取事实前必须执行，且清洗掉的噪声不得进入报告）：
   - 页面导航与位置面包屑（如"您所在的位置>…>要闻>正文"）；
   - 媒体自引与机构抬头（如"证券日报微信 证券日报微博"、研报落款邮箱/机构署名）；
   - 小编式引导语与推广尾巴（如"点击查看原文""下载 APP"）；
   - 与该公司无关的同页其他条目（接口按关键词召回，`chunk` 中段可能夹带其他公司内容）。

拼接产物（§7 映射）落盘为该场景的输入结构：

```json
{
  "scene": "2",
  "scene_name": "核心推荐逻辑",
  "chapter": "2",
  "target": "短期逻辑 / 长期逻辑",
  "company": "宁德时代",
  "query": "【宁德时代】投资观点",
  "sources_desc": "研报披露的公司最近半年的数据",
  "window": { "start": "2026-03-23 00:00:00", "end": "2026-09-23 23:59:59" },
  "returned": 6,
  "kept": 3,
  "chunk_chars": 1489,
  "text": "……（按 showTime 倒序拼接的 chunk 文本，`\n` 分隔）……",
  "items": [ { "showTime": "2026-09-18 09:12:00", "chunk": "……" } ]
}
```

`--all --with-meta` 时外层再包一层场景 map，且每个场景附 `sources`（溯源清单，供
`data.json` 各章节 `sources` 字段组装与 hover+click 溯源渲染）：

```json
{
  "company": "宁德时代",
  "as_of": "2026-09-23",
  "scene_order": ["1", "2", "3.1", "3.2", "4", "5.1", "5.2", "6", "7", "8", "9"],
  "failed_scenes": [],
  "scenes": {
    "1": {
      "…": "（见上）",
      "sources": [
        { "title": "宁德时代:H股公告(翌日披露报表)", "time": "2026-09-23 18:48:27",

```

## 8. 场景 1 事件筛选标准（与 `prompts/01-公司近况跟踪.md` 一致）

**可纳入催化事件时间表**：业绩/财务类、业务/战略类、技术/产品类、管理/治理类、政策/行业类、产能/全球化类，且**必须能从 `chunk` 中读到具体事件主体与事实量级**（金额、GWh、股数、项目名、时间节点等）。

**必须剔除**：纯短期股价波动（涨停/跌停/单日涨跌幅）、纯交易类（龙虎榜、北向资金、融资余额、大宗交易）、纯市场情绪类（概念轮动、题材炒作）、无实质业务影响的股价异动解读。

> 注：场景 1 的召回会同时包含公告、资讯与研报，研报类内容同样按上表筛选——
> **只保留基本面事实，机构评级与目标价一律不得进入报告**。
>
> 催化事件时间表的主供数为事件库通道（`newsEventSearch` / `futureEventSearch`，见 `事件库-取数规范.md`），**事件库返回的事件行同样适用上表筛选标准**。

**来源可信度分级（仅用于取舍，不影响用词）**：

| 等级 | 典型来源 | 处理 |
|---|---|---|
| 高 | 交易所公告、公司公告（溯源标记对应公告 PDF） | 可单独成行 |
| 中 | 主流财经媒体（证券时报、证券日报、中国证券报、21 世纪经济报道等） | 可单独成行 |
| 低 | 自媒体 / 百科 / 非持牌资讯聚合（微信、MBA 百科、内容农场等） | **不得单独成行**，须与高/中等级来源的信息交叉验证一致后才可使用；无法交叉验证则丢弃 |

## 9. 失败与降级（零幻觉）

- 单场景 `mx_finance_search` 返回为空 / 工具报错 / raw 文件缺失 → 记录 `error` 并按场景降级：

| 场景 | 降级顺序 |
|---|---|
| `1` | 近况文字段与催化事件时间表**分通道独立降级**：① 文字段无事实支撑 → 只渲染催化事件时间表（基于既有上下文提炼文字段，不得编造）；② 文字段与表格皆无事实支撑 → 章节 1 **只保留一级章标题「1 公司近况跟踪」**。催化事件时间表由事件库通道供数，其降级见 `事件库-取数规范.md` §5，不随场景 `1` 失败整体取消 |
| `2` | 只保留一级章标题「2 核心推荐逻辑」，不输出任何解释性空状态 |
| `3.1` / `3.2` | 对应单元格整行不渲染（该行随数据缺失删除）；`prompts/03-公司简介.md` 负责判定 |
| `4` / `6` / `7` / `8` | 文字段改由该章 MQL 数据生成（**不得**编造接口未返回的事实）；MQL 亦无数据则整段不渲染 |
| `5.1` / `5.2` | 同 `4`：退化为仅用 MQL 集中度数据生成，或整段不渲染 |
| `9` | 只保留一级章标题「9 公司风险提示」 |

- **时间只来自 `showTime`**：禁止从 `chunk` 正文里抽取日期充当事件时间（正文日期可能是引用历史或转发日期）。
- **事件与数字只来自本次检索返回的 `chunk`（或已取到的 MQL 数据）**：禁止补充检索未返回的事件、金额、订单量、客户名、机构名、评级或目标价。
- 催化事件时间表**行数不足 4 行照实输出**，严禁复制/变体重复凑数。
- 单元格禁止空状态占位；"预期影响"确实无法判断时，仅可使用统一降级文本"事件影响待后续披露"。
- 合规用词以 `prompts/01-公司近况跟踪.md` §三 为准，其中禁用词表与 `validate_report.py` 的 `BANNED` 列表一致。

## 10. 执行方式（Agent 编排 + 脚本归一化）

### 10.1 并发提交编排（每批 3–4 个，**不得串行**）

11 个场景**彼此无依赖**（`query` 唯一变量是公司名称，窗口由系统日现算，互不引用对方结果），因此检索**按批并发提交**：

| 批次 | 并发提交的场景（批次内同时发起） | 场景数 |
|---|---|---|
| A | `1`、`2`、`3.1`、`3.2` | 4 |
| B | `4`、`5.1`、`5.2`、`6` | 4 |
| C | `7`、`8`、`9` | 3 |

规则（硬约束）：

1. **每批上限 4 个**：同一批内的场景**一次性并发发起**（4+4+3 共 3 批），**禁止**逐个等待返回后再发下一个。
2. **批次间无依赖**：三批的先后不改变任何结果，可按 A→B→C 递进，也可在工具允许的并发上限内整体推进；并发上限不足时按批退让，**但仍以"一批 3–4 个"为最小并发单元**。
3. **并发只改变提交与返回的时序，不改变以下口径**：`query` 原文（§3）、时间窗（§4）、`raw/{scene}.json` 落盘契约（§5）、加工 4 步（§6）、场景顺序 `1 → 2 → 3.1 → 3.2 → 4 → 5.1 → 5.2 → 6 → 7 → 8 → 9`（§7 / `news_api.py` 的 `SCENE_ORDER`）。
4. **落盘禁止串号**：并发返回后必须按 `query` 与场景键一一对应写入 `raw/{scene}.json`（如 `【X】主要客户` → `raw/5.1.json`、`【X】主要供应商` → `raw/5.2.json`）；写错文件等同取数失败。
5. **失败隔离**：单场景返回为空 / 工具报错 / 写盘失败**不影响**同批其它场景；该场景按 §9 降级，其余场景照常归一化。
6. **禁止**为"凑并发"改写句式、复用其它场景的返回、或把同一场景的返回拆到多个 raw 文件。
7. 并发批次划分与 `scripts/news_api.py` 的 `SCENE_BATCHES` 逐项一致，**改动须两处同步**。
