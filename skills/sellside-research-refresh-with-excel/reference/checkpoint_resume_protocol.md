# 阶段检查点与续跑协议

## 状态机

合法状态为：

`PENDING → IN_PROGRESS → CONFIRMED`

任一执行或验证失败可进入 `BLOCKED`。修复后从 `BLOCKED` 回到 `IN_PROGRESS`，不得直接写成 `CONFIRMED`。

阶段验证通过后直接写为 `CONFIRMED`，无需人工确认，可一次性连续跑完所有阶段。

## `run_manifest.json`

至少记录：

- `task_id` 和目标版本。
- 阶段状态、开始/完成时间。
- 输入及产物的绝对路径、SHA-256 和字节数。
- 实际验证命令、结果和回执。
- 限制、失败类别、最后成功工件和唯一建议下一步。

## 次日续跑

1. 读取计划进度表、`run_manifest.json` 和最近的 handoff。
2. 重新计算已确认阶段的输入和产物哈希。
3. 哈希一致时直接复用，不重跑。
4. 某输入变化时，仅将直接受影响阶段及其下游重置为 `PENDING`。
5. 依赖 skill 接口变化时，重新验证该 skill 直接参与的 handoff 及下游阶段。
6. 从首个 `PENDING` 或 `BLOCKED` 阶段继续；不得依赖聊天记忆猜测状态。

## 阶段 4 强制独立续跑（硬规则）

阶段 3 handoff `CONFIRMED` 后，阶段 4 **必须在新上下文/新任务段执行**，不得在承载阶段 0–3 的长上下文尾部继续。动机：预算将尽或上下文过长时，宿主会把「诚实阻塞」逼成「绕过引擎手写交付」——这是本轮复发的第一诱因（2026-10-14 上汽集团事件）。

- 注入内容仅限：`stage-3-handoff.json`、参考 PDF 路径、B 底稿路径、宿主 `SKILL.md` §4 指针。
- 新任务段的首个动作是运行 `scripts/check_bundle.py` 自检；`BLOCKED` 即停止（bundle 缺失走编译路径，不现场重建）。
- 禁止在阶段 4 任务段内评估"预算/上下文是否够"并以此降级为宿主手写 MD/HTML；任何偏差都被 `assemble_delivery.py` 来源门禁判 `STAGE4_BYPASSED`/`FAIL`。
- 阶段 3 之后宿主停止承担仿写决策职责，只做数据交接；是否继续的决策由阶段 4 独立段依 §4 规程执行。

## 失败保存

失败时不得删除成功工件。保存：

- 原始错误和错误类别。
- 最后通过的验证和工件。
- 尚未完成的唯一下一步。
- 是否需要用户输入或外部服务恢复。

不允许用空文件、默认值或缺少哈希的输出伪装阶段成功。
