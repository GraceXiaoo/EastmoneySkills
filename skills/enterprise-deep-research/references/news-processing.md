# 信源排序与模块输入截断

本文件统一规定 `enterprise-deep-research` 全部 15 个分析模块的信源排序和最终 input 截断。规则在本地组装输入时执行，不修改任何 `references/analysis-prompts/*.md` 原文，不改变 MQL、Python 兜底、资讯检索或板块路由规则。

## 适用范围

- 全部 15 个模块独立执行 **16000 字符**的最终 input 上限，包含 ESG分析和重点关注；不是整份报告共用 16000 字符。
- 前 14 个原始数据模块只处理当前板块的 `block_data_package` 与 `block_news_package`，不得跨板块合并排序或补位。
- MQL 数据及同源 Python REST 兜底数据属于专业数据库数据，优先保留；资讯按其真实来源分类、权威度、发布时间排序。
- 重点关注只处理前序模块已经生成的分析正文，详见下方专用规则，不新增原始数据或资讯。
- 以完整信源单元剔除，不切片、不摘要改写、不拆分单条信源来凑长度。完整原始包保留在底稿，截断仅作用于本次传入 prompt 的副本。

## 信源单元

- 一条资讯为一个单元，含完整标题、必要业务元数据、正文或检索返回摘要；不得临时截取摘要替代已有正文。
- 一个已登记的专业数据库数据集为一个单元，含其完整表格、日期、单位和业务口径说明。单元边界在计算长度前按原始数据集确定，不按长度临时拆行、拆表或删字段。
- `{{数据}}` 和 `{{资讯}}` 的单元共同决定保留优先级，但入选后仍分别写入各自占位符，不能互相混传。
- 单条信源即使独自超过可用空间，也必须整条剔除，并停止添加后续信源。

## 资讯条目字段归一

每条资讯尽量保留以下字段；字段名以 `mx-finance-search` 实际返回为准，归一后的字段只用于本地排序和展示：

```json
{
  "title": "<标题>",
  "content": "<正文或摘要>",
  "source": "<来源名称>",
  "source_category": "<来源分类>",
  "authority_level": "<权威度文本或 V2 等级>",
  "information_type": "<informationType 原值，如 NOTICE/REPORT/NEWS>",
  "published_at": "<发布时间>"
}
```

- 若原始结果提供 `authorityLevel`，优先保留原值；`authority_level` 只是本地归一字段，不得伪造不存在的等级。
- 若原始结果提供 `informationType`，保留原值；不得仅因 `NOTICE`、`REPORT`、`LAW`、`BOND` 来自检索数据库，就将这些资讯改标为专业数据库数据，分类以实际来源元数据为准。
- 缺少来源分类、权威度或发布时间时，不得补造；排序时将缺失值放在同类已知值之后，并在内部审计 `notes` 中注明字段缺失。

## 来源分类优先级

来源分类按以下顺序从高到低排序，数值越小优先级越高：

| 排序值 | 来源分类 | 内容范围 |
|---:|---|---|
| 0 | 专业数据库数据 | 当前模块的 MQL 数据、同源 Python REST 兜底数据及实际标明此分类的信源 |
| 1 | 其它信源 | 公告、研报、新闻、互联网资讯等；保留原分类文本 |

来源分类是第一排序键，只规定专业数据库数据优先。其它信源不额外按公告、研报、新闻类别分层，直接比较权威度和发布时间。缺少分类的信源不能推定为专业数据库数据，按其它信源处理并登记缺失。

## 权威度排序

在来源分类相同的前提下，按资讯权威度由高至低排序：

| 排序值 | 权威度 V2 | 常见原始值 |
|---:|---|---|
| 0 | 最高 | `L1`、`权威度：最高` |
| 1 | 高 | `权威度：高` |
| 2 | 较高 | `权威度：较高` |
| 3 | 中等 | `L2`、`权威度：中等` |
| 4 | 较低 | `L3`、`权威度：较低` |
| 5 | 低 | `权威度：低` |
| 6 | 极低 | `权威度：极低` |
| 7 | 未知 | 字段缺失或无法映射 |

若接口只返回 `L1/L2/L3`，按 `L1 > L2 > L3` 处理；若同时返回中文权威度文本，以中文权威度文本映射为准。权威度是第二排序键。

## 发布时间排序

在来源分类和权威度都相同的前提下，按 `published_at` 由近及远排序。可解析的日期优先于缺失或无法解析的日期；日期相同保持接口原始顺序。缺失发布时间不得用系统日、抓取日、报告期或业务发生日补造。

## 全模块输入截断规则

### 上限

每个模块最终传入其对应 prompt 的完整 input 文本长度上限为 **16000 个字符**。按本地组装后实际字符串的 `len(rendered_input)` 计算，不按 token、字节数或仅资讯正文估算。恰好 16000 字符允许传入，超过则不允许。

`rendered_input` 包括：

1. 对应 prompt 替换占位符后的完整文本，保留所有固定指令；
2. 企业名称和允许传入的必要上下文；
3. 当前模块入选的完整数据与资讯，或重点关注入选的前序分析结果，包含与其绑定的有效原始引用；
4. 实际传入的标题、表头、分隔符、日期、单位等全部包装文本。

同一内容在模板中出现多次时按实际出现次数计长；不计入未传给模型的审计底稿。组装时保留材料实际返回的有效原始引用及其绑定信息，并将实际送入 prompt 的引用文本计入长度；仅排除内部审计字段。排序、截断仍使用原始元数据，不删改资讯事实内容。

### 排序后顺序截断

1. 固定信源单元边界，按“专业数据库数据优先 → 权威度由高至低 → 发布时间由近及远 → 原始顺序”稳定排序。
2. 先将所有可选信源占位符置空，完整渲染固定提示词和企业名称，检查固定部分是否已超限。
3. 从排序后的第一条开始，逐条将完整单元放回其对应的 `{{数据}}`、`{{资讯}}` 或前序分析槽位，重新渲染完整 input 后计长。
4. 加入第 N 条后长度不超过 16000，则保留第 N 条；超过则撤回第 N 条，剔除第 `[N, ∞)` 条范围的所有信源并立即停止。不得跳过第 N 条再寻找更短的后续条目补位。
5. 不得对单条内容做字符切片、只保留标题或拆成多个条目。高优先级数据库数据也必须遵守硬上限；数据库单元放不下时整单元剔除，不能继续追加低优先级资讯。
6. 再次渲染并校验 `len(rendered_input) <= 16000` 后才允许送入分析。正文只能依据实际入选的材料；空数据/空资讯按原 prompt 处理。
7. 将截断前后长度、单元数量、保留和剔除的单元标识、首个超限单元及原因登记在本地审计信息中。

### 固定内容已超限

如果所有可选数据、资讯或前序分析槽位都置空后，固定提示词、企业名称及必要包装文本仍超过 16000 字符：

- 不修改用户 prompt 原文，不发起该模块分析，也不发送超限 input；
- 登记 `status=failed`、`truncation_reason=input_base_exceeds_limit`，说明固定输入超限；
- 不允许沿用“清空资讯后仍超限也继续生成”的旧处理方式。

## 重点关注

重点关注同样执行 16000 字符硬上限，但输入仍只能来自前 14 个模块的分析结果：

1. 每个非空模块的完整分析正文 为一个不可拆分单元；未选模块保持空槽位。没有对应模板占位符的槽位不计入候选输入或字符预算。
2. 从各前序模块的本地输入审计记录读取实际入选材料的分类、权威度和发布时间，按上述相同排序键确定优先级；多个材料取其中优先级最高者作为该正文的排序依据。不从正文解析引用编号。没有对应元数据时标为未知，不依据报告生成时间伪造发布时间，也不新增检索。
3. 排序键完全相同时按固定 14 槽位顺序保留。排序只决定哪些完整正文入选，实际渲染仍按原 prompt 的槽位位置，不调整用户提示词结构。
4. 执行相同的前缀截断：首个放不下的模块正文及后续候选全部剔除，其输入副本的对应槽位置空；已有报告章节及完整底稿不删除、不改写。
5. 截断后同步更新输入副本的 `analysis_results`、`prompt_inputs`、`active_blocks`、`empty_blocks`，随完整单元保留或移除对应原始引用；不得留下脱离入选材料的引用。审计元数据单独保存，不将原始表格、资讯全文、来源排序信息或企业类型标记混入重点关注 prompt。

## 截断审计

每个模块都登记独立的处理结果；资讯包仍保留入选的完整资讯条目，不得仅保留拼接纯文本。原始包、截断后的输入副本与审计记录分开保存。通用审计结构如下：

```json
{
  "block_name": "<当前模块名>",
  "prompt_file": "<当前模块对应的本地 prompt 路径>",
  "processing": {
    "status": "ready",
    "sort_keys": ["source_category_rank", "authority_rank", "published_at_desc", "original_index"],
    "input_limit": 16000,
    "input_length_before_truncation": 0,
    "input_length_after_truncation": 0,
    "source_units_before_truncation": 0,
    "source_units_after_truncation": 0,
    "news_items_before_truncation": 0,
    "news_items_after_truncation": 0,
    "kept_unit_ids": [],
    "dropped_unit_ids": [],
    "first_excluded_unit_id": null,
    "truncated": false,
    "truncation_reason": ""
  }
}
```

`unit_id` 仅供内部审计区分完整信源条目，不传入分析 prompt，也不出现在报告中。重点关注的单元数是入选前序模块正文数，其资讯条目数为 0。因超限剔除时登记 `truncation_reason=input_limit_exceeded`；固定内容超限时 `status=failed`，不存在可发送的 `input_length_after_truncation`，记为 `null`。

保留完整底稿和内部审计记录；排序或截断不改变原始记录。报告按句内溯源规则使用入选材料的有效原始引用，不输出本地审计编号或审计清单。
